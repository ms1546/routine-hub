## 7. 対応策をアプリ全体に適用する際の懸念点

※ 実装はまだ行わない。適用前に検討したい点のみ記載。

| 懸念 | 内容 | 提案 |
|------|------|------|
| **日本語ユーザーと英語表記** | 対応策は Routine / Public・Private / Energy Level・high-medium-low と英語統一。日本語メインのユーザーには「公開・非公開」「低・中・高」の方が直感的に分かりやすい可能性がある。 | 英語統一を貫くか、ラベルは英語のまま option や補足だけ日本語にするか、方針を決めておく。 |
| **「適用」→「反映」の範囲** | ボタン・トースト・モーダルなど「適用」が多数ある。コード・変数名（ApplyRoutineForm, apply 等）はそのままで、表示文言だけ「反映」にすると、開発者視点では「適用」と「反映」が並存してやや紛らわしい（表示だけなので大きな問題ではない）。 | 表示文言のみ「反映」にし、コードは apply のままでもよい。必要なら「反映」の意味づけを用語表に 1 行書いておく。 |
| **AIカスタマイズ = Routune の解釈** | 表の対応策「AIカスタマイズ = Routune 適用=反映」が短文のため、実装時に解釈が分かれる可能性。「Routune」は typo か Routine か、AIカスタマイズは機能名として残すのか、「Routine を反映する」のような言い回しに変えるのかを明確にしたい。 | 用語表または 1. の表に 1 行で「適用＝カレンダーへの反映」「AIカスタマイズ＝Routine の時間調整機能名」などと補足するとよい。 |
| **description を全体的に非表示** | 設定・マイページの description に加え、「人気のRoutineを発見…」「コミュニティで最も…」のようなキャッチも不要、とある。初見ユーザーがページの目的を理解しにくくなる可能性。 | 意図的にミニマルにするなら問題ない。トップや一覧で「何のページか」が分かる別の手がかり（見出しやアイコンなど）があるかだけ確認するとよい。 |
| **Block 表記と意味の伝わりやすさ** | 「時間ブロック」→「Block」にすると短く揃うが、「Block」だけだと「時間の一塊」であることが初見で伝わりにくい場合がある。 | Block に統一する方針なら、初出時だけ「時間の Block」やツールチップで補足するか、用語表で定義を書いておく。 |
| **バリデーション・エラーメッセージ** | zod 等の「Descriptionは必須です」「Nameは必須です」「ブロック名は必須です」など。UI を英語統一するなら、エラーも "Name is required" などに揃えるか、日本語のまま「名前を入力してください」に統一するか、方針が必要。 | セクション 3 のメッセージも用語表に含め、画面表記と一致させる（英語なら英語、日本語なら日本語で統一）。 |
| **セクション 5 との齟齬** | セクション 5 では「公開/非公開」「ルーチン」「負荷レベル 低・中・高」等を推奨案として記載。今回の対応策は Routine / Public・Private / Energy Level と英語寄り。 | 実装では 1. の対応策を正とする。セクション 5 は「旧案・参考」と注記するか、対応策に合わせて 5 の表を更新すると、実装者が迷わない。 |
| **テスト・Storybook** | 文言変更により、`getByText('適用')` やスナップショットなど、文言に依存するテストやストーリーが落ちる。 | 文言変更と同時に、該当するテスト・Storybook の文言を更新する。 |
| **AI プロンプト内の用語** | プロンプトや Langfuse では「適用」「カスタマイズ」「エネルギーレベル」等が使われている可能性がある。UI を「反映」「Energy Level」にしても、AI 向けの説明は日本語のままの方がよい場合がある。 | UI 用語と AI 用語の住み分けを決める（ユーザーに見える部分だけ対応策に合わせ、プロンプト内は現状維持でよいか、など）。 |
| **用語の置き場所** | 文言を直書きのまま変更すると、将来 i18n や用語の一括変更をするときにまたコンポーネントを触ることになる。 | 可能なら、先に用語表または定数ファイルに寄せてから置き換えると、次のステップ 1 と整合する。 |
